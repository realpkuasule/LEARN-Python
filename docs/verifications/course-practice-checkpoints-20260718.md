## 自动决策

1. 每章三个“实战练习”按文档顺序形成阻塞点；最后一个检查点固定为 `final-challenge/pass`。
2. 第 1 章的 Prompt 对比、需求描述和架构梳理无法由 Python 沙箱客观判定，采用显式人工确认，不解锁代码运行。
3. 普通代码实践采用 `practice` 执行模式，只运行学员代码一次；不追加终局隐藏测试，也不结算奖励。
4. 正式终局采用 `formal` 执行模式，继续使用既有期望输出或隐藏测试，并且只有正式通过才完成章节。
5. 第 2 章的五节点流程已由用户人工通过，保持不变。
6. 第 6 章热身题声称示例存在边界 bug，但原示例已能输出第 9 回合；已把错误示例改为 `range(1, 9)`，使题目、提示和修复目标一致。
7. 讲解中的代码示例、选读和可选扩展不强制形成检查点；只有明确标为实战或网站终局的任务阻塞剧情。

## 契约与验证

- OpenAPI `ExecutionRequest` 明确要求 `mode: practice | formal`。
- 故事标记支持 `confirm | run | success | output | error | pass`。
- 非代码确认不能由执行结果误完成，运行按钮保持锁定并提示在左侧确认。
- 自动测试逐章验证检查点 ID 唯一、顺序固定、全部位于正文、终局检查点最后出现且要求为 `pass`。
- 服务测试验证隐藏测试不会污染普通练习，正式评测仍不泄漏隐藏输入与期望结果。
- 第 6 章浏览器抽样确认首个 `output` 节点前运行锁定、到达节点后按钮切换为「运行练习」。普通 starter code 以 practice 模式运行后正确提示“尚未满足当前实践要求”，Boss 仍为 `3/3 HP`、隐藏测试仍为 `0/3`。
- 浏览器抽样首次发现 practice 的 `1/1` 结果被误显示为 Boss `1/3`；已将 Boss 测试进度限定为 formal 运行并完成同路径回归。
